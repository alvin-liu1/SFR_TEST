# Coding Rules

## Existing Coding Conventions

当前项目以成对 .h/.cpp 分模块，类名 PascalCase；成员 m_ 前缀，方法以 camelCase 为主但保留 ReadConfig、AreaCutJudge、SLR 等历史名称。函数花括号通常换行，控制语句存在同行风格；按相邻代码保持缩进。
中文 Doxygen 文件/类/函数注释、分段说明和单位注释较多。头文件同时存在 pragma once 和 include guard，不统一改写。使用 std::vector、cv::Mat、unique_ptr、fstream 和 future 管理资源；错误风格混用返回码、控制台和异常，新增代码应遵守当前模块契约。
本节是已观察习惯，不意味着所有现存行为都是最佳实践。

## AI Coding Rules

1. 优先最小修改。
2. 禁止无关重构。
3. 禁止修改与当前 TASK 无关的文件。
4. 不允许因为“不确定”就扫描整个 Repository。
5. 信息不足时先报告缺少的上下文。
6. 修改公共接口前必须分析影响范围。
7. 修改关键数据结构前必须分析影响范围。
8. 不允许删除无法确认用途的代码。
9. 不允许声称没有实际执行的测试已经 PASS。
10. 不允许为了代码更漂亮而改变已经工作的逻辑。
11. 必须保留现有代码风格。
12. 修改完成必须提供 git diff。
13. 修改完成必须说明修改原因。
14. 发现 TASK 本身可能有问题时停止实施并报告。
15. 未经允许禁止进行大范围架构重构。

## Project-specific Constraints

- 普通任务先读基线文档并定位模块；源码读取和协作细则以 AI_WORKFLOW.md 为准。
- 不擅自修正数值公式、频率单位、Gamma 或 H/V 定义；先确定参考值和容差。
- 修改 AreaNum、阈值、AOI 格式、结果列或返回码，必须列出调用方、消费者和兼容性影响。
- Mat 裁剪默认共享内存；修改原地处理和并发须分析 alias、重叠 AOI、线程生命周期及独立输出路径。
- 不改变既有有效配置/输出格式和默认值，除非 TASK 明确授权。
- 设备脚本、DeleteOriginPic 和失败转移回退属于有副作用路径；验收需明确输入副本和设备授权。
- 不覆盖或提交用户无关改动，不将缓存、构建产物及本地敏感路径作为新增实现。
- 只运行与改动相关的必要检查，记录命令、退出码及失败/未执行原因。文档变更无需伪造算法测试。
- 每次交付提供实际 diff（新增未跟踪文件需暂存后 git diff --cached 或 git diff --no-index）；git diff --stat 不能替代完整差异审阅。
